## 0. The thing that confuses everyone first: four independent deployment surfaces

Git is only one of them. **Code can be live in production while existing in no merged branch.**

| Surface | Deployed by | Notes |
|---|---|---|
| **Vercel frontend** | merge/push to `main` on GitHub | auto-deploys; keeps last good build if one fails |
| **Supabase edge functions** | `supabase functions deploy <name>` — **NOT git** | committing the source does nothing on its own |
| **Supabase data rows** (`params`, `team_data`) | using the app, or a sync function | |
| **pg_cron schedules** | applying a migration to the DB | `supabase db push`; committing the .sql does nothing |

So "is it live?" always needs asking per surface. Verification commands in §5.

## 4. ⚠ Known gap in Stage 7 — found at 19:15 IST, NOT yet fixed

`sync-catalogue` is deployed but its cron is deliberately unscheduled, and there are **three** reasons
not to schedule it until these are handled:

**(a) `status` would be clobbered.** The live master has **5 SKUs with `status: 'Confirmation Pending'`**
— `29ZVW`, `E3MPF`, `TENX4`, `WUTDS`, `XP5EV` (all MYK Laticrete). Zoho's item status vocabulary is
only `active`/`inactive`, and `mapItemsToMaster` does `status: it.status ?? "active"`. So a sync would
rewrite those 5 to `active`, and since the engine filters `status === "active"`, they'd go from
**excluded** to **getting real stocking targets**. Ops parked them deliberately.
*Fix:* same shape as `inventorisedAt` — let Zoho win only for `active`/`inactive` and preserve any other
stored value. Add a test.

**(b) SKUs present in the CSV master but absent from Zoho would be dropped.** Master is 2,092; Zoho
`/items` returns 2,083. A sync replaces the master wholesale, so ~9+ SKUs vanish.
*Fix:* decide whether Zoho is authoritative for *existence*, or whether unmatched SKUs should be
retained. Probably retain, with a report.

**(c) `cf_inventorised_at` does not exist in Zoho yet.** Sandy is creating and populating it.
Already handled safely — Zoho wins only where it has a value, else the stored value stands (verified:
`invAtFromZoho: 0`, `invAtFromStored: 2074`, distribution preserved exactly). **Tell him to verify with
ONE SKU + a dry run before populating all 2,083** — `invAtFromZoho` should go 0 → 1.

**(d) Old-style SKU codes still trickle in.** On 2026-07-28 at ~19:30 Sandy re-uploaded the invoice CSV
to consolidate `TIL-MYK-LCW-3MM` (93 rows, absent from `skuMaster`) onto `8FWE3` (Active, DC) — qty
reconciled exactly, 387 + 226 = 613, and window unknown-SKU rate improved from 0.08% to **0.02%**. This
is the tail of the same 2026-07-01 org migration. Expect more stragglers; the unknown-SKU rate is the
metric that finds them, and `sync-invoices`' coverage guard now watches it automatically every night.

⚠ **`diag-items` will mislead you on (c).** It checks `custom_fields[]` and `custom_field_hash`, both of
which are absent on `/items`; the fields actually arrive as **top-level `cf_*` keys**. It reports "no
custom fields" while seven sit in plain sight. `catalogueMap.ts` `customField()` checks all three shapes.
