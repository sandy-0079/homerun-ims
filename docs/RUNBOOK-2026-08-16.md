## 2b. If you edit the floors sheet before tonight's run

Adding SKUs is safe, and that is a property of the guard rather than luck:

```js
dropPct = (liveKeys.length - parsedKeys.length) / liveKeys.length * 100   // guard trips above 20
```

More SKUs makes `parsedCount > liveCount`, so `dropPct` goes **negative** and cannot trip. Same for
`floorDropPct`. **The guard only ever blocks losses**, never additions — deliberately, since ops
adding floors is the normal case and removing 20% of them is not.

| what you do | what happens |
|---|---|
| Append new SKU rows | Written. `change.counts.added` reflects them |
| Append a row for a SKU already in the sheet | **Last row wins** — the append rule shipped today. Counted and named in the digest |
| Blank a value cell | `0` for floors, i.e. floor removed. Normal |
| Add a floor for a SKU that also has a **ceiling** | ⚠ The ceiling still wins. No warning here — only the *ceiling* upload preview flags that conflict, so it will pass silently |
| Type `2.5`, `-1`, `N/A`, or leave a `#REF!` | **Hard stop, `invalid_value`.** Whole file refused, stored floors intact, and the digest now **names the cell** |
| Add an unknown store column (`DS07 Min`/`DS07 Max`) | **Hard stop, `unknown_ds`** — `DS_LIST` must gain DS07 in both the engine and the sync first |
| Filter the sheet so no rows show | **Hard stop, `empty`** — the guard `force` cannot bypass |

So the realistic failure from editing tonight is a typo, and it **fails closed**: nothing is written,
yesterday's floors stay live, and — unlike before today — the email tells you which cell. No rush to
fix it; the next night picks it up.

⚠ One consequence worth expecting: if you add floors tonight, `change.counts.added` will be non-zero
and `overrodeManualUpload` will still fire (§2). Both are correct.

## 3. The engine run — `params/toTargets`

```bash
curl -s "$SB/rest/v1/params?select=payload->refreshedAt,payload->inputs,payload->invValue&id=eq.toTargets" -H "apikey: $KEY"
```

| field | expected | why |
|---|---|---|
| `refreshedAt` | **06:15 IST**, not 05:45 | two slots run; the second rewrites the row. `05:45` means the 06:15 run **failed** |
| `inputs.invoiceDataThrough` | yesterday's IST date | the run timestamp alone cannot tell you the inputs were fresh |
| `inputs.skuCeiling` | = SKUs in `team_data/global.skuCeiling` | ⚠ counts `team_data` directly — matches whether or not the engine used them |
| `invValue.max` | **whatever the dry run below predicts** | this is the actual proof the ceilings applied |

⚠⚠ **DERIVE THESE, DO NOT TRUST A NUMBER WRITTEN HERE.** The ceiling file is expected to change —
more SKUs may be added at any time — and an earlier draft of this runbook hardcoded values that were
wrong within the hour. One read-only command regenerates every expectation:

```bash
npx vite-node scripts/dryrun-sku-ceiling.mjs     # writes NOTHING
```

It prints `Inv Value (Max): <uncapped> -> <capped>` and the exact list of capped cells **for whatever
is stored right now**. The nightly `invValue.max` must equal its `<capped>` figure.

and if every biting cap sits on a store with sales, those branches never execute. It has 5 unit tests

no-demand store before a run.

## If something is wrong

| symptom | first move |
|---|---|
| No email at all | `nightly-digest` cron, then `function_logs where event_message like 'booted%'` |
| Floors refused | Read `skuFloorSyncStatus.reason`. Stored floors are intact. Fix the sheet; the next night picks it up |
| `refreshedAt` reads 05:45 | The 06:15 run failed — read `params/engineRunStatus` |
| Ceilings not applied (`invValue.max` ≈ ₹8.53Cr) | `POST /api/run-engine {"mode":"dry"}` and compare `invValue`; it writes nothing |
| Anything looks wrong with a cap | Rollback is the `🗑 Clear` button on the SKU Ceilings card — writes `{}`, all caps gone on next page load |
