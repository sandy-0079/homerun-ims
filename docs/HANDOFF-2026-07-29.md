## 5b. Agreed plan (aligned 2026-07-29 evening, NOT yet built)

**Order of work:** reconcile → Stage 5 → freshness timestamp → SKU-floor sync → Stage 6.
The timestamp deliberately precedes Stage 6 so that when the engine starts running unattended, you can
already see whether it ran.

**Where the inputs stand.** Invoices, SKU Master and Purchase Prices are automated. New DS Floor Qty,
SKU Floors and Dead Stock are **already store-once** — `saveTeamData` persists them (`App.jsx:3154-3156`),
startup reloads them (`3019-3021`), and `sync-catalogue`'s read-merge-write preserves them. So they are
NOT daily-refresh inputs and never were. **The remaining blocker is not an input — it is that nothing
writes `params/toTargets` except a human clicking Apply.**

**⚠ Stage 6 architecture — CHANGED from the earlier design.** Run the headless engine as a **Vercel Cron
in THIS repo**, not a Supabase edge function. Verified 2026-07-29: `src/engine/` has **zero** browser
dependencies (no `window`, `document`, `localStorage`, `navigator`, worker APIs), and `index.js` is a
clean barrel export — so a Vercel function can `import` it directly.
- This **eliminates** the drift problem rather than detecting it. The earlier plan was "stamp the engine
  commit SHA so IMS can warn about divergence"; with a Vercel cron there is nothing to stamp, because the
  cron and the browser bundle deploy from the same commit and import the same file.
- It also lets the run reuse `loadParamConfigRows()` — the helper that exists precisely because three
  places rebuilt `activeParams` by hand and two got it wrong.
- Copying the engine into a Deno function would recreate the exact two-implementations problem we refuse
  to accept for the TO tool.

**Freshness timestamp.** Store the metadata INSIDE `params/toTargets`, so the TO tool gets it free — it
already reads that row:
`refreshedAt` · `invoiceDataThrough` · `catalogueSyncedAt` · `engineCommit` · `degraded`.
- ⚠ **`invoiceDataThrough` matters more than `refreshedAt`.** A run timestamp says a computer did
  something; it does not say the answer is current. If the invoice sync fails two nights, the engine
  still runs on time and still stamps *today* over three-day-old data. A fresh-looking timestamp over
  stale inputs is worse than none.
- Placement — IMS: a pill in the header strip (`styles.header`, `App.jsx:80`), right-aligned via
  `marginLeft:auto` so it shows on every tab; fuller per-input breakdown on Upload Data.
  TO tool: beside the existing stock freshness, reusing `isFresh()` from `homerun-to/src/sync.js`, and
  fetched with the targeted JSON-path pattern already used for `stockUploadedAtPerDS`.
- Cheapest first step: `toTargets.refreshedAt` **already exists** and is written on every Apply — it is
  simply displayed nowhere. Surface it before Stage 6 exists, enrich afterwards.

**SKU-floor sync from a Google Sheet.** Runs after the invoice window (~04:00 IST), which is also after
`sync-catalogue` — required, or a SKU newly created in Zoho is not yet in `skuMaster` and its floor is
skipped for no reason. Decisions (Sandy, this session):
- **Sheet is AUTHORITATIVE**: a floor whose SKU is absent from the sheet is **dropped**. Deliberately
  chosen over merge-semantics, and chosen without the row-collapse guard. ⚠ Consequence to remember: a
  filter left applied, or a partial load, removes floors. Mitigation is **reporting, not blocking** —
  removals are listed in full in the status row, so a wipe is visible rather than silent.
- **Values: integers ≥ 0, no ceiling.** `0` removes. Decimals rounded/rejected, negatives rejected. A
  fat-finger (1000 for 100) is reported among the largest changes but not blocked.
- Unknown SKUs are **skipped and named** — old-style codes still trickle in (`FUT-DURA-24-18-8`,
  `ASI-PAI-EXT-POLE-10FT` appeared in today's unknown list), so a silent skip would mean ops believes a
  floor is live when it is ignored.
- Also validate: DS against `DS_LIST` (`DS07`/`DSO2`/`DS02 Bileshivale` all fail differently),
  duplicate `SKU×DS` rows (reject or report — same shape as a pincode claimed by two DSes), and **the
  header row**, because a revoked publish makes Google serve an HTML error page that `parseCSV` will
  happily turn into garbage rows where every SKU is unknown — indistinguishable from "no changes
  tonight" unless the header is checked.
- Report floors that can never take effect: Dead Stock overrides all floors to 0, Supplier zeroes
  everywhere, Inactive is excluded. Legitimate no-ops that will otherwise look like bugs to ops.
- **Still needed from Sandy:** the sheet URL, the column layout (SKU×DS matrix vs `SKU,DS,Qty` rows),
  and whether it is published to web. Publishing makes it readable by anyone with the URL.
