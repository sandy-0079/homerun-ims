
It exits `0` clean, `1` with issues, `2` on a STOP condition. What it covers:

| check | expect |
|---|---|
| `params/toTargets.targets` → union of `perDS` keys | **DS01–DS06 only**, no DS07/DS08 |
| `params/toTargets.inputs.invoiceDataThrough` | yesterday's date |
| `params/toTargets.invValue` | **flat vs the previous night — derive both figures from `params/digestHistory`, never from a number written here.** Night-on-night drift is ~0.1–1.6%; a bigger jump is the signal. ⚠ An earlier draft of this row quoted a ₹7.99Cr/₹5.60Cr "band" copied from 2026-08-05. By 2026-09-19 the real value was ₹10.30Cr/₹7.34Cr and the band would have failed a perfectly healthy night. |
| `params/skuFloorSyncStatus.ok` | `true` |
| `params/invoiceSyncStatus.publishedAt` | stamped overnight |
| digest email 06:30 IST | delivered green |

⚠ `toTargets.refreshedAt` will read **06:15**, not 05:45. `engine-run-nightly` is
`15,45 0 * * *` UTC — two slots — and the second rewrites it. `05:45` would mean the 06:15
run FAILED. This has nearly caused a healthy system to be reported broken before.

If anything is off, **stop and diagnose before deploying anything.** A bad night plus four
fresh deploys is two variables.

## Step 4 — prove the branches are reachable

it, a mis-wired DS07 looks identical to a correctly-wired empty one until go-live morning.

Invoke `sync-stock` with the anon Bearer (as the crons do):

```
{"branches":["DS07"]}     → expect team_data/global.stockUploadedAtPerDS.DS07 to appear
{"branches":["DS08"]}     → expect ...DS08 to appear
```

Both should return 200 with `branches: ["DS07"]`. A timestamp proves reachability. **No
timestamp = stop**, and check the branch id and the child-location setup before Monday.

one event proves the migration *and* reachability. DS08 hand-invoked: HTTP 200, 2,782 SKUs.

live stores. That is what separates "empty store, correctly wired" from "unreachable branch",

Tell ops to add **DS07 and DS08 columns in one edit** to the SKU Floors sheet, and populate
DS07 (mirroring DS06 gives a ~2,300-SKU opening assortment). Column position is irrelevant —

⚠ **Sheet-before-code fails the nightly sync.** `parseFloorSheet` hard-stops with
`unknown_ds`, fail-closed: the previous floors stay live and nothing updates. The sync runs
`5,55 23 * * *` UTC = **04:35 / 05:25 IST**.

⚠ **Adding a NEW SKU ROW is a live change to that SKU's DC, today.** `isFlooredSKU` tests
whether the SKU *key* exists (`runEngine.js:413`), not whether a floor is non-zero, and an
all-zero row still creates the key — which flips the DC from the rate-based formula to the
floored one. Filling DS07 cells on rows that already exist is inert.

## Step 5b — SKU CEILINGS csv (no ordering constraint — already safe)

⚠⚠ **DO NOT treat this like the floors sheet. The two look alike and are opposite in both
respects.**

|  | read by | ready? | blank means |
|---|---|---|---|
| Floors sheet | `sync-sku-floors` — **edge function**, not deployed | ⚠ wait for Step 2 | blank = 0 = **no floor** |
| Ceilings csv | `parseSkuCeilingCsv` — **the browser**, already live | ✅ safe now | blank = **NO CAP** |

The ceilings file is parsed in the deployed frontend against `[...DS_LIST,"DC"]`, which already
knows all eight stores (`App.jsx:2306`), and the template download already emits `DS07 Cap` /
`DS08 Cap` (`App.jsx:2855`). So ops can download, edit and re-upload it at any point — before or
after the edge deploys.

**No action is actually required before go-live.** No cap = uncapped = whatever the strategy
computes, which is correct for a new store. Touch this file only if ops wants DS07 capped from
day one.

⚠⚠ **IF THEY DO TOUCH IT: leave the new cells BLANK, NEVER `0`.** In this file
**blank = NO CAP and 0 = CAP AT ZERO** — they are opposites, unlike the floors sheet where
blank and 0 both mean "no floor". A well-meaning `0` in `DS07 Cap` pins the store at 0/0 after
go-live while attribution, the gate and every status row read perfectly healthy. That is hours
of debugging for a habit that felt cautious.

⚠ The existing 815 ceiling entries are untouched by any of this. Re-uploading the downloaded
template round-trips losslessly (pinned by a test against `buildSkuCeilingCsv`), but it is a
**replace-entirely** write — so download fresh, edit, re-upload; never re-upload a stale copy.

## Step 7 — go-live day (DS07, ~Mon 2026-09-21; DS08 a week later)

Operator decision 2026-09-18: **floors + pincodes + flip in ONE Apply**, not split.

1. Upload the pincode remap on the Upload Data tab. The UI now shows a diff before applying —
   `128 → N pincodes · X moved · Y added · Z removed`. **A non-zero "removed" means rows went
   missing, not moved.** `params/pincodeMap` is replace-entirely; a short file silently
   un-maps pincodes and the donor stores quietly re-inflate.
2. Logic Tweaker → **Store Status** → untick DS07.
3. Add DS07 to **`newDSList`** in the same screen — ⚠ prod's list is
   `["DS04","DS05","DS06","DS03"]` and a shallow merge means prod wins, so the
   `DEFAULT_PARAMS` entry does **not** put it there.
4. Set the DS07 plywood **capacity** to 300 thick / 150 thin on the Plywood tab.
   ⚠⚠ **CORRECTED 2026-09-19 — the earlier text here was wrong, and wrong in the dangerous
   direction.** It said DS07 "is not a node in `params/plywoodNetworkConfig`, so plywood SKUs
   land 0/0 there until it is." Live data says otherwise: **DS07 and DS08 are already full
   plywood nodes under all four brands** (GreenPly, ArchidPly, CenturyPly, Action Tesa), each
   with `covers:["DS07"]` / `["DS08"]`. What is actually at zero is `params/global.dsCapacities.DS07`
   = `{thin:0, thick:0}`, and the capacity trim reads:

   ```js
   // plywoodNetwork.js applyCapacityTrim
   if (!capacity || capacity <= 0) continue;   // zero capacity SKIPS the trim
   ```

   So zero capacity is **NO CAP AT ALL**, not zero stock. It is invisible today only because
   DS07 has no pincodes and the gate zeroes it. The moment pincodes are remapped and the store
   is unticked, DS07 plywood allocates **uncapped**. Skipping this step does not cost you a
   store reading 0/0 — it over-allocates one. (DS06 sits at 300/150; DS01/DS02 at 400/200.)
5. **Apply & Re-run Model.**

**Expected signature:** DS07 targets appear, donor stores (DS01/DS02/DS05) **drop**, network
Inv Value **roughly flat**. Attribution *moves* demand rather than creating it. A jump means
something double-counted.

**Residual accepted 2026-09-18:** donors replenish ~10–20% leaner Mon–Tue against an
unchanged sell rate, because they lose the HAL catchment before DS07 opens on Wednesday.
Watch DS01/DS02/DS05 in Stock Health on Tuesday; the 14:30 TO run can top up by hand.

⚠ Do **not** upload pincodes without flipping the store live in the same Apply. Measured:
remapping 19 pincodes to a *gated* store moved 179 live-store cells and 132 DC values — the
donors give the demand away and the gated store cannot claim it. The Logic Tweaker warns on
both halves of this; the warning is load-bearing, not cosmetic.
